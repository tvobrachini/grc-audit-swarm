# Limitations and accuracy

- **Decision support only.** The output is a draft for a qualified auditor. It is not an audit opinion and does not replace engagement supervision.
- **Not benchmarked yet.** There are no measured accuracy, precision, time-saving or cost figures. The LLM-layer evaluation harness ([docs/EVALUATION.md](EVALUATION.md)) defines the metrics and scenarios, but no real-model run has been published, and its answer key is still an unreviewed draft.
- **QA is another LLM.** Temperature 0 lowers variance on hosted models but does not remove it. A QA approval does not show the output is correct.
- **Reviewer identity is self-declared unless per-reviewer tokens are configured.** By default the API uses one shared token: the name in the approval trail is what the reviewer typed (`identity_source: "declared"`), so the segregation-of-duties checks compare typed names only. With `REVIEWER_TOKENS_FILE` set, the name comes from the reviewer's own token (`identity_source: "authenticated"`). That authenticates a reviewer to this application only: it is not single sign-on, there is no MFA, a token works for whoever holds it, and anyone who can write the tokens file or run the CLI on the server can issue a token under any name. Entries recorded before tokens were configured stay declared.
- **Approval trail.** The hash chain makes edits to the stored trail detectable; it does not prevent them. Without `VAULT_ENCRYPTION_KEY`, anyone who can write the sessions file and the anchor file can rebuild a consistent trail. With the key, they also need the key. Entries cut from the end are only detected against the anchor file, and only if that file is kept somewhere the sessions file's writer cannot also edit — see [Security and data handling](SECURITY-AND-DATA.md#approval-trail-hash-chain-and-anchor-file).
- **Generation provenance does not make runs reproducible.** Recording the provider, model, prompt fingerprint and temperature behind a phase run tells you *what was configured*, not what will happen again: LLM output is not deterministic even from identical inputs, so two runs with the same recorded fields can still produce different artifacts. A recorded model name is also what the process was configured to call, not proof that a provider's servers, an intermediate proxy or a provider-side alias didn't resolve it to something else.
- **Evidence vault.** Each record's digest is stored in the same writable JSON file as the payload. Without encryption the digest detects accidental corruption only. With encryption, editing a record without the key is detected, but deleting a record or replacing it with an unencrypted one is not. The vault does not prove the absence of tampering. A verified quote shows the words are in the evidence; it does not show the conclusion drawn from them is right. Matching is exact, so paraphrases show as not verified.
- **AWS coverage.** Live collection covers the IAM account password policy, IAM user MFA, and S3 bucket public access. The Fieldwork crew has no other evidence tools, so controls outside these reads have no collected evidence behind them. Within them:
  - The S3 verdict combines the bucket policy status, bucket ACL grants to `AllUsers` / `AuthenticatedUsers`, and account- and bucket-level Block Public Access. Whether a policy is public is AWS's own evaluation (`GetBucketPolicyStatus`); the tool does not parse policies. It does not cover S3 access points (or their policies), Multi-Region Access Points, object-level ACLs, or presigned URLs. A policy that grants access to specific other AWS accounts is not "public" in AWS's sense, so cross-account sharing is not flagged. Per-bucket reads use one S3 client and rely on botocore's automatic region redirect for buckets in other regions; this is tested with stubs and moto only, not against a live multi-region account.
  - The MFA check lists IAM users only. The account root user is not returned by `iam:ListUsers`, so root MFA is not covered. It reports whether any MFA device is assigned, for every user, and does not check whether the user has console access.
  - The password-policy evidence is the policy as returned. "No policy set" is reported as a finding; judging whether a policy is strong enough is left to the auditor and the agents.
- **Standalone MCP server.** `src/swarm/mcp_server.py` uses the same evidence logic as the CrewAI tools, but it does not register evidence in the vault or redact its final output (AWS error messages are redacted).
- **OSCAL.** `oscal.json` is a real, schema-validated OSCAL 1.2.1 Assessment Results document (see [Architecture](ARCHITECTURE.md#oscal-export) and DECISIONS.md ADR-005), not merely OSCAL-shaped. Its remaining limits: there is no OSCAL assessment plan, system security plan, catalog or profile, so control IDs are the engagement's own RACM IDs rather than catalog IDs; schema validation does not check OSCAL's Metaschema constraints or FedRAMP-specific rules, and no external OSCAL validator runs in CI; and the audit-specific conclusions (test-of-design / test-of-effectiveness, deficiency classification) live in project-namespaced props that a generic OSCAL consumer will not interpret.
- **Reviewer identity again, for generation provenance.** A generation run record does not by itself prove a human reviewed the artifact it names — only that the review action in the trail is tied to that run's record. It inherits the identity limits of the rest of the trail (declared names by default; per-reviewer tokens if configured).
- **Demo data.** DEMO_MODE output is fixed sample content, labeled as demo data in every artifact. It is not evidence and not a finding about any system.
- **Standards.** References to IIA Global Internal Audit Standards 12.3 (formerly 2340) and 14.6 (formerly 2330), PCAOB AS 1215 and NIST OSCAL are design inspiration. The project makes no compliance claim against any of them.
