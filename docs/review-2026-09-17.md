# GRC Audit Swarm — Code Review + Internal-Audit Standards Research

Mode: BOTH (criteria-based code review + authoritative-source research on the internal-audit standards the repo cites). Repo: `/home/tvobrachini/Work/grc-audit-swarm`, reviewed at commit `5e33b92`.

## Executive summary

Code review found one CRITICAL and several PRIMARY defects, concentrated in the evidence vault's integrity guarantee and the human-approval gate logic — the two features the repo leans on hardest for its "compliance" story. Standards research found that the repo's citations (PCAOB AS 1215, IIA 2330, IIA 2340) are **directionally reasonable but technically overstated**: none of the cited standards mandate SHA-256 hashing or any cryptographic mechanism, and PCAOB AS 1215 is scoped to public-company financial-statement audits, a scope the tool (general-purpose GRC/IT audit) doesn't clearly sit in. The NIST OSCAL claim is accurate in spirit but the implemented schema is missing a NIST-required field. 9 fan-out lanes ran (5 code, 4 standards); verification pass confirmed every substantive claim, with one citation line-number correction.

## Findings

### 1. Evidence Vault — integrity claim doesn't match implementation (CRITICAL)

`src/swarm/evidence.py`'s class docstring states: *"Implements PCAOB AS 1215 and IIA 2330 compliance by enforcing immutable hashing of payloads"* (evidence.py:76). In practice:

- `verify_exact_quote()` does only a substring check — `return exact_quote_claim in payload` (evidence.py:152) — and never re-validates the stored `sha256` field against the payload. Tampering with `raw_payload` after storage goes undetected by this function despite the "immutable hashing" claim.
- Standards check (see §2 below): neither IIA 2330 nor PCAOB AS 1215 requires hashing at all, so "enforcing immutable hashing" is the repo's own technical embellishment layered onto standards that don't ask for it — and the hashing that exists isn't wired into the verification path anyway.

Secondary code issues in the same file:
- Overbroad `except (KeyError, json.JSONDecodeError, OSError, Exception)` (evidence.py:153) masks the actual failure cause.
- `_get_fernet()` is `@lru_cache(maxsize=1)` (evidence.py:8, 25) — rotating `VAULT_ENCRYPTION_KEY` at runtime silently has no effect until process restart.
- Redundant base64 decode→encode round-trip on the same bytes (evidence.py:34-38).

Verified sound: path-traversal protection via realpath+commonpath check (evidence.py:133-136), hash-before-encrypt ordering, and conservative fail-closed exception defaults (returns `False`).

### 2. Standards citations for the Evidence Vault — overstated (PRIMARY, research)

- **IIA 2330 "Documenting Information"** (2017 Standards) requires: *"Internal auditors must document sufficient, reliable, relevant, and useful information to support the engagement results and conclusions."* Its 2024 successor (14.6, "Documenting the Engagement") requires: *"Internal auditors must document information and evidence to support the engagement results."* Neither mentions hashing, cryptography, or immutability — both are technology-agnostic. Source: theiia.org official reference pages.
- **PCAOB AS 1215 "Audit Documentation"** requires (verbatim, official PCAOB text): 7-year retention from report release date (§.14); assembly into final form within 14 days of report release (§.15); no deletion after that date, though information may be *added* with date/preparer/reason metadata (§.16). No cryptographic or technical integrity mechanism is prescribed anywhere in the standard. Source: pcaobus.org, AS 1215.
- **Scope mismatch**: AS 1215 is a PCAOB standard under Sarbanes-Oxley and by its own jurisdiction governs audits of public companies' financial statements / internal control over financial reporting. `grc-audit-swarm` positions itself (README, CASE_STUDY) as a general-purpose GRC/IT controls audit tool (e.g. AWS cloud security) — not specifically a financial-statement audit tool for public companies. Citing AS 1215 as a governing standard here is a likely scope/category error; the IIA standards the repo also cites are the applicable framework for general internal/IT audits.

**Verdict**: SHA-256 hashing + quote verification is a reasonable *engineering choice* in service of "reliable, reperformable evidence," but it is not something either cited standard requires, and one of the two citations (AS 1215) probably doesn't apply to this tool's actual use case at all.

### 3. IIA 2340 "Engagement Supervision" — human-gate justification is a loose reading (PRIMARY, research)

The repo cites "IIA 2340 stamping" (README lines 23, 59, 66) to justify mandatory human-approval gates between each automated audit phase. The standard's own text (IIA official summary, theiia.org): *"Engagements must be properly supervised to ensure objectives are achieved, quality is assured, and staff is developed. The extent of supervision required will depend on the proficiency and experience of internal auditors and the complexity of the engagement. The chief audit executive has overall responsibility for supervising the engagement... Appropriate evidence of supervision is documented and retained."*

This mandates *supervision and documented review*, scaled to context — it does not explicitly mandate discrete approval gates between phases of one engagement. The repo's human-gate design is a reasonable way to *implement* the supervision principle, but citing "2340" as though it specifically mandates phase-gating overstates what the standard says. (Caveat: full IIA standard text is members-only paywalled; this reading is based on IIA's own public summary page, cross-checked independently in the verification pass and confirmed consistent.)

### 4. Human-approval gates can be bypassed or fail silently (PRIMARY, code)

In `src/swarm/audit_flow.py` / `src/swarm/state/machine.py` / `src/swarm/state/repository.py`:

1. **Silent double-rejection**: after the one built-in auto-retry, a second QA rejection transitions to `QA_REJECTED_PHASE_X` and returns silently — no exception, no loud failure signal (audit_flow.py:129-133, 203-207, 284-290).
2. **Approval-trail ordering bug**: `self.state.approval_trail.append(...)` runs *before* the state-machine transition guard that actually performs the gate transition (audit_flow.py:45-54, 58-67) — a mistimed call can leave an approval-trail entry recorded even though the real transition was skipped, undermining the very audit trail the IIA citations are meant to support.
3. **Gate bypass via direct call**: calling `generate_fieldwork()` / `generate_reporting()` directly auto-transitions through the gate check (`if self.machine.status == WAITING_HUMAN_GATE_1: self.machine.approve_gate_1()`) with no independent verification that a human actually approved (audit_flow.py:152-154, 226-228).
4. **No concurrency control**: `session_manager.py`'s read-modify-write session persistence has no locking — concurrent requests can lose updates (last-write-wins) (session_manager.py:30-48, with the actual race in `save_session`/`update_session` a few lines below).
5. **Gate 3 is effectively dead-wired**: `audit_flow.py:295` calls `self.machine.complete_audit()` directly instead of `complete_phase_3()`, and the code never calls `approve_gate_3()` anywhere — `WAITING_HUMAN_GATE_3` (machine.py:15) is reachable in the state machine's transition table but never actually exercised by the flow. Note: the state machine itself *permits* `RUNNING_PHASE_3 → COMPLETED` directly (machine.py:43), so this is a wiring/design gap in `audit_flow.py`, not a defect in the state machine's transition rules.

Secondary: `FlowRepository.save()` (state/repository.py:34-41) makes 3 separate non-transactional session-manager calls — a mid-sequence exception leaves state partially persisted; no automatic re-run mechanism after `QA_REJECTED_PHASE_X`.

### 5. NIST OSCAL Assessment Results — naming is fine, schema is incomplete (PRIMARY, research + code)

The repo's `OSCAL_SAR_Schema` (schema.py:142-144) and README's description of translating findings "into a machine-readable NIST OSCAL format (`OSCAL_SAR_Schema`)" (README:40) are reasonably named: NIST's own abbreviation is *"SAR = Security Assessment **Results**"* (paired with SAP, POAM), and the official model is the "OSCAL Assessment Results Model" (root element `assessment-results`). Source: pages.nist.gov/OSCAL-Reference.

However, NIST's required top-level structure is `metadata`[1], `import-ap`[1] ("identifies the OSCAL-based assessment plan... which imports... the system security plan"), `result`[1..∞]. The repo's actual implementation:

```python
class OSCAL_SAR_Schema(BaseModel):
    metadata: OSCAL_SAR_Metadata
    results: List[OSCAL_SAR_Result]
```
(schema.py:142-144, confirmed by direct read)

is missing the required `import-ap` field entirely — there's no linkage to an assessment plan, which NIST's spec treats as mandatory. This was independently confirmed twice (main-thread grep + verification-pass re-check).

Minor terminology note: NIST's own docs state this model *"was created based on the information requirements of a FedRAMP Security Assessment Report"* — FedRAMP's "SAR" (Report) and NIST OSCAL's "SAR" (Results) are adjacent-but-distinct terms; the repo's variable name doesn't disambiguate which sense it means, though this is cosmetic next to the missing field.

### 6. API auth — one real misconfiguration, otherwise solid (PRIMARY + clean)

`src/api/main.py:25-26` sets `allow_origins=["*"]` together with `allow_credentials=True` — this combination is invalid per the CORS specification (a wildcard origin cannot be paired with credentialed requests); if any proxy/browser combination normalizes or misconfigures around this, it's a real security misconfiguration to fix.

Everything else checked out clean: token comparison uses `secrets.compare_digest()` (auth.py:29, timing-safe); an unset `API_AUTH_TOKEN` raises HTTP 503 rather than silently disabling auth (auth.py:17-21); error messages are generic and non-leaking (auth.py:32); every `/api/*` router carries the auth dependency (main.py:37, 40, 46); `/health` is intentionally unprotected (main.py:50-52); Bearer-token parsing is correct (auth.py:25-27).

### 7. AWS evidence collection — one completeness gap (PRIMARY + verified-correct)

`list_public_s3_buckets` calls `s3.list_buckets()` directly with no pagination handling (aws_tools.py:75-76), unlike `list_iam_users_with_mfa`, which correctly paginates via `client.get_paginator("list_users")` (aws_tools.py:38). This asymmetry means large accounts could get incomplete evidence collected without any signal — a direct threat to the "sufficient... evidence" principle both IIA 2330 and PCAOB AS 1215 actually do require.

Secondary: per-user MFA check failures are caught and coerced to `has_mfa = "Unknown"` (aws_tools.py:49-50), conflating "the API call failed" with "the user genuinely has no MFA" inside the audit record itself.

Verified correct: the README's 12-digit AWS account ID redaction claim holds up — regex `(?<!\d)\d{12}(?!\d)` (evidence.py:19) correctly handles both standalone account IDs and ones embedded in ARNs, applied both before storage (evidence.py:93) and before evidence is returned to agents (aws_tools.py:30, 64, 139). No hardcoded credentials found; all three AWS tool functions return explicit error strings on top-level exceptions rather than silently reporting a false "Pass."

### 8. Documentation self-contradiction + robustness gaps (PRIMARY)

- README.md:88's prose — *"Priority order Gemini → OpenAI → Groq"* — directly contradicts README.md:119-125's own table, which lists the real 5-tier order: Ollama → NVIDIA → Gemini → OpenAI → Groq. `llm_factory.py`'s actual sequential checks (lines 18, 29, 49, 53, 57: OLLAMA → NVIDIA → GEMINI → OPENAI → GROQ) match the table, confirming the prose sentence is simply stale/wrong.
